1 What RAG is and why

RAG = Retrieval-Augmented Generation. Instead of hoping the model remembers everything about the game, we first search for matching pieces of knowledge, then paste them into the prompt, so the model answers from concrete facts.

Why it matters here:

  • The model does not know the game in detail. Recipes, alloy ratios, block drops — none of that is in the model's training data with any reliability.
  • Without RAG the model makes things up (hallucinates). “Bronze is 50% tin” sounds confident and is wrong.
  • Knowledge changes (game updates, mods). Re-ingesting is far easier than retraining a model.

✗ Without RAG (bare model)

“How do I make tin bronze?” → “Mix tin and copper in the right proportions.” — vague, no numbers, sometimes wrong.

✓ With RAG

→ the database returns tinbronze: ingot-tin 8-12%, ingot-copper 88-92% → “Tin 8–12% + copper 88–92%, smelted in a crucible.”

2 Embedding: text → a vector of numbers

Computers do not compare text “by meaning” — they compare numbers. An embedding turns a piece of text into a vector, a list of numbers (here 1024 numbers, because the bge-m3 model produces 1024 dimensions). The key trick: texts with similar meanings get similar vectors. 

# the embedding model turns a sentence into a vector of 1024 numbers
"how to make bronze"   →  [ 0.021, -0.144, 0.077, 0.512, ... ]   # 1024 numbers
"recipe for tin alloy" →  [ 0.019, -0.139, 0.081, 0.498, ... ]   # VERY similar ↑
"jak zrobić brąz"      →  [ 0.024, -0.151, 0.070, 0.505, ... ]   # Polish, still close
"how to tame a horse"  →  [ -0.31, 0.402, -0.22, 0.05, ... ]    # something else entirely

In the project this is vsai/embeddings.py: one HTTP call to Ollama embeds a whole batch of texts:

How does the model “know” that bronze ≈ tin alloy? It was trained on billions of sentences and learned that these words show up in similar contexts. An embedding is a compressed map of meaning learned from text. A multilingual model like bge-m3 learned that map across languages, so “brąz” and “bronze” land close together.

3 Vector space (intuition)

A vector of 1024 numbers is a point in 1024-dimensional space. That cannot be drawn, so picture just 2 dimensions. Texts with similar meanings lie close together and form clusters. The player's question also becomes a point — and we look for its nearest neighbours.

The question (yellow) lands next to the “metallurgy” cluster → the database returns those documents, not the ones about animals.

4 Cosine distance, step by step

If we look for the “closest” points, we have to define what close means. The most common measure for text is cosine similarity: it looks at the angle between two vectors and ignores their length.

The formula

cosine_similarity(A, B) = (A · B) / (|A| · |B|)

where:
  A · B   = dot product      = a₁·b₁ + a₂·b₂ + ... + aₙ·bₙ
  |A|     = length of A      = √(a₁² + a₂² + ... + aₙ²)

cosine_distance = 1 − cosine_similarity
  • similarity = 1 → the vectors point the same way (0°) → same meaning → distance 0
  • similarity = 0 → perpendicular (90°) → unrelated → distance 1
  • similarity = −1 → opposite (180°) → distance 2

A worked example (in 2D, so it can be done by hand)

Take three vectors and work out which one is closer to the question A:

A and B point in a similar direction (small angle) → high similarity. C veers off → low similarity.

A vs B:

A = (4, 3)   B = (5, 2)

A · B = 4·5 + 3·2 = 20 + 6 = 26
|A|   = √(4² + 3²) = √25 = 5
|B|   = √(5² + 2²) = √29 ≈ 5.385

similarity = 26 / (5 · 5.385) = 26 / 26.93 ≈ 0.966   ← very similar!
distance   = 1 − 0.966 = 0.034

A vs C:

A = (4, 3)   C = (-2, 4)

A · C = 4·(-2) + 3·4 = -8 + 12 = 4
|A|   = 5
|C|   = √((-2)² + 4²) = √20 ≈ 4.472

similarity = 4 / (5 · 4.472) = 4 / 22.36 ≈ 0.179   ← weakly related
distance   = 1 − 0.179 = 0.821
Result: document B (distance 0.034) is much closer to the question than document C (0.821), so the database returns B. The project does exactly the same, only in 1024 dimensions instead of 2 — the maths is identical.

Why the angle and not the length?

Because a vector's length often depends on how long the text is, not on what it means. The word “bronze” and a paragraph about bronze can have vectors of different lengths but the same direction (topic). Cosine only looks at direction, so it is robust to text length. That is why it is the default choice for semantic search.

Good to know: for vectors of length 1 (normalised), cosine, dot product and Euclidean distance give the same ranking of neighbours. They differ when vectors are not normalised. What changes in every case is the scale of the numbers — which matters as soon as you set a threshold on them.

6 Which metric this project uses

The original collection was created without a metric, so ChromaDB silently used its default, l2 (squared Euclidean distance). The rebuilt knowledge base sets cosine explicitly and records which embedding model built it (vsai/kb.py): 

client.create_collection(
    "vintage_story_kb",
    metadata={"hnsw:space": "cosine", "embed_model": "bge-m3"},
    embedding_function=None,   # we always pass vectors ourselves
)
  • The metric cannot be changed on an existing collection — switching meant creating a new one and re-ingesting.
  • kb.open_collection() refuses to open a collection built with a different embedding model, or one that still uses l2. Vectors from different models are not comparable, so mixing them would give nonsense results.
  • Cosine distances fall between 0 and 2, which makes the relevance threshold (RAG_MAX_DISTANCE) easier to reason about.

7 Retrieval: how the database finds results (HNSW)

Measuring the distance from the question to every chunk gets slow on large collections. So ChromaDB uses HNSW (Hierarchical Navigable Small World) — a clever graph that finds the “almost nearest” neighbours without checking everything. This is called ANN (Approximate Nearest Neighbours).

def search(collection, query, n_results=5, model=None) -> list[Hit]:
    vector = embed([query], model=model)[0]
    result = collection.query(query_embeddings=[vector], n_results=n_results,
                              include=["documents", "distances", "metadatas"])
    ...   # → [Hit(text, distance, metadata), ...], closest first
A trap worth knowing: query always returns the nearest N — even when the nearest document has nothing to do with the question. Without checking the distance, the bot would paste junk into the prompt. That is why the bot keeps only hits closer than RAG_MAX_DISTANCE (default 0.5); if none is left, the prompt tells the model to say it has no reliable information. 8 Chunking — why we cut the text up

We do not store whole long pages, but chunks of ~150–200 words with a small overlap. The reasons:

  • Precision: a short chunk = one topic = a cleaner vector. A whole page mixes topics.
  • Context budget: only a handful of chunks go into the prompt, not the whole wiki.
  • Overlap: the words repeated across a chunk boundary stop a thought from being cut in half.
def chunk_text(text, max_words=200, overlap=30):
    words = text.split()
    if len(words) <= max_words:
        return [text]
    chunks, i = [], 0
    while i < len(words):
        chunks.append(" ".join(words[i:i + max_words]))
        i += max_words - overlap        # step back 30 words = the overlap
    return chunks

Search strategies

  • Pure vector search (current): meaning only. Weak on exact names and codes (e.g. ingot-tinbronze).
  • Hybrid (vector + BM25): combines meaning with ordinary keyword matching. Best for recipes with specific names.
  • Reranking (cross-encoder): fetch 20 candidates, then a precise model re-sorts them and keeps the top 3. A big jump in precision.
  • MMR (Maximal Marginal Relevance): keeps the results diverse, so you do not get the same fact three times.
