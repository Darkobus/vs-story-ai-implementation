1 Czym jest RAG i po co

RAG = Retrieval-Augmented Generation — „generowanie wspomagane wyszukiwaniem". Zamiast liczyć, że model sam pamięta wszystko o grze, robimy tak: najpierw wyszukujemy pasujące fragmenty wiedzy, a potem doklejamy je do promptu, żeby model odpowiadał na podstawie konkretnych faktów.

Dlaczego to ważne w tym projekcie:

  • Model nie zna Twojej gry w szczegółach. Receptury, proporcje stopów, dropy bloków — tego nie ma w wiedzy modelu.
  • Bez RAG model zmyśla (halucynuje). „Brąz to 50% cyny" — brzmi pewnie, jest błędne.
  • Wiedza się zmienia (aktualizacje gry, mody). Łatwiej podmienić wpis w bazie niż trenować model od nowa.

✗ Bez RAG (czysty model)

„Jak zrobić cynbrąz?" → „Wymieszaj cynę z miedzią w odpowiednich proporcjach." — ogólnik, brak liczb, czasem błąd.

✓ Z RAG

→ baza zwraca tinbronze: ingot-tin 8-12%, ingot-copper 88-92% → „Cyna 8–12% + miedź 88–92%, stop w tyglu."

2 Embedding: tekst → wektor liczb

Komputer nie porównuje tekstu „po znaczeniu" — porównuje liczby. Embedding to zamiana fragmentu tekstu na wektor, czyli listę liczb (tu: 768 liczb, bo model nomic-embed-text produkuje 768 wymiarów). Kluczowa magia: teksty o podobnym znaczeniu dostają podobne wektory. 

# model embeddingowy zamienia zdanie na wektor 768 liczb
"how to make bronze"  →  [ 0.021, -0.144, 0.077, 0.512, ... ]   # 768 liczb
"recipe for tin alloy" →  [ 0.019, -0.139, 0.081, 0.498, ... ]   # BARDZO podobny ↑
"how to tame a horse"  →  [ -0.31, 0.402, -0.22, 0.05, ... ]    # zupełnie inny

W projekcie robi to klasa OllamaEmbeddingFunction — wysyła tekst do Ollamy i odbiera wektor:

class OllamaEmbeddingFunction(EmbeddingFunction):
    def __call__(self, input: list[str]) -> Embeddings:
        embeddings = []
        for text in input:
            # POST do Ollamy: {"model": "nomic-embed-text", "prompt": text}
            res = ollama_embed(text)
            embeddings.append(res["embedding"])   # wektor 768 liczb
        return embeddings
Skąd model „wie", że bronze ≈ tin alloy? Bo był trenowany na miliardach zdań i nauczył się, że te słowa pojawiają się w podobnych kontekstach. Embedding to skompresowana mapa znaczeń wyuczona z tekstu.

3 Przestrzeń wektorowa (intuicja)

Wektor 768 liczb to punkt w przestrzeni 768-wymiarowej. Nie da się tego narysować, więc wyobraźmy sobie tylko 2 wymiary. Podobne znaczeniowo teksty leżą blisko siebie i tworzą „skupiska" (klastry). Pytanie gracza też zamieniamy na punkt — i szukamy najbliższych sąsiadów.

Pytanie (żółte) ląduje obok klastra „metalurgia" → baza zwraca te dokumenty, nie te o zwierzętach.

4 Odległość kosinusowa — krok po kroku

Skoro szukamy „najbliższych" punktów, musimy zdefiniować co znaczy blisko. Najpopularniejsza miara dla tekstu to podobieństwo kosinusowe: patrzymy na kąt między dwoma wektorami, ignorując ich długość.

Wzór

podobieństwo_kosinusowe(A, B) = (A · B) / (|A| · |B|)

gdzie:
  A · B   = iloczyn skalarny   = a₁·b₁ + a₂·b₂ + ... + aₙ·bₙ
  |A|     = długość wektora A  = √(a₁² + a₂² + ... + aₙ²)

odległość_kosinusowa = 1 − podobieństwo_kosinusowe
  • podobieństwo = 1 → wektory wskazują w tę samą stronę (kąt 0°) → identyczne znaczenie → odległość 0
  • podobieństwo = 0 → wektory prostopadłe (kąt 90°) → brak związku → odległość 1
  • podobieństwo = −1 → przeciwne (kąt 180°) → odległość 2

Przykład liczbowy (w 2D, żeby dało się policzyć ręcznie)

Weźmy trzy wektory i policzmy, który jest bliżej pytania A:

A i B wskazują podobny kierunek (mały kąt) → wysokie podobieństwo. C odchyla się mocno → niskie.

Liczymy A vs B:

A = (4, 3)   B = (5, 2)

A · B = 4·5 + 3·2 = 20 + 6 = 26
|A|   = √(4² + 3²) = √25 = 5
|B|   = √(5² + 2²) = √29 ≈ 5.385

podobieństwo = 26 / (5 · 5.385) = 26 / 26.93 ≈ 0.966   ← bardzo podobne!
odległość    = 1 − 0.966 = 0.034

Liczymy A vs C:

A = (4, 3)   C = (-2, 4)

A · C = 4·(-2) + 3·4 = -8 + 12 = 4
|A|   = 5
|C|   = √((-2)² + 4²) = √20 ≈ 4.472

podobieństwo = 4 / (5 · 4.472) = 4 / 22.36 ≈ 0.179   ← słabo powiązane
odległość    = 1 − 0.179 = 0.821
Wynik: dokument B (odległość 0.034) jest dużo bliżej pytania niż dokument C (0.821). Baza zwróci więc B. W projekcie dzieje się dokładnie to samo, tylko w 768 wymiarach zamiast 2 — matematyka identyczna.

Dlaczego kąt, a nie długość?

Bo długość wektora często zależy od długości tekstu, a nie od znaczenia. Zdanie „brąz" i akapit o brązie mogą mieć różne długości wektorów, ale ten sam kierunek (temat). Kosinus patrzy tylko na kierunek → jest odporny na długość tekstu. Dlatego to domyślny wybór dla wyszukiwania semantycznego.

5 Kosinus vs euklides vs iloczyn skalarny

MetrykaCo mierzyZalety / wadyNazwa w ChromaDB
Kosinusowa Kąt (kierunek), ignoruje długość Standard dla tekstu; odporna na długość dokumentu cosine
Euklidesowa (L2) Odległość „w linii prostej" między punktami Intuicyjna, ale czuła na długość wektora; dla nieznormalizowanych embeddingów bywa gorsza dla tekstu l2 domyślna!
Iloczyn skalarny
(dot / inner product)		 Kierunek i długość naraz Najszybsza; jeśli wektory są znormalizowane, daje to samo co kosinus ip
Ciekawostka: dla wektorów o długości 1 (znormalizowanych) kosinus, iloczyn skalarny i euklides dają ten sam ranking sąsiadów. Różnice pojawiają się, gdy wektory nie są znormalizowane — a embeddingi z Ollamy nie zawsze są. Dlatego wybór metryki ma znaczenie (patrz niżej).

6 Ważne: ten projekt domyślnie używa L2, nie kosinusa

Pytałeś o „odległości cos" — i tu jest niespodzianka. Kolekcja w tym projekcie jest tworzona tak: 

collection = client.get_or_create_collection(
    name="vintage_story_wiki",
    embedding_function=OllamaEmbeddingFunction()
    # BRAK metadata={"hnsw:space": "cosine"}  ←  nikt nie ustawił metryki!
)

Gdy nie podasz metryki, ChromaDB domyślnie używa l2 (kwadrat odległości euklidesowej), a nie kosinusa. Czyli mimo że „semantycznie" myślimy o kosinusie, baza realnie liczy euklides.

To jest realny kandydat na poprawkę. Dla wyszukiwania tekstu zwykle lepszy jest kosinus. Żeby go włączyć, trzeba stworzyć kolekcję od nowa z jawną metryką (metryki nie da się zmienić w istniejącej kolekcji): 
collection = client.get_or_create_collection(
    name="vintage_story_wiki",
    embedding_function=OllamaEmbeddingFunction(),
    metadata={"hnsw:space": "cosine"}   # ← jawnie kosinus
)

Więcej o tym i o innych poprawkach: Ulepszenia.

7 Retrieval: jak baza znajduje wynik (HNSW)

Gdyby baza miała policzyć odległość pytania do każdego z ~1900 chunków, byłoby to wolne przy dużych zbiorach. Dlatego ChromaDB używa HNSW (Hierarchical Navigable Small World) — sprytnego grafu, który pozwala znaleźć „prawie najbliższych" sąsiadów bez sprawdzania wszystkiego. To tzw. ANN (Approximate Nearest Neighbors).

pytanie
(tekst)
→
embedding
768 liczb
→
HNSW szuka
najbliższych
→
top-N chunków
+ ich odległości

W kodzie to jedna linijka — cała złożoność jest schowana w bibliotece:

results = wiki_collection.query(
    query_texts=[translated],   # Chroma sama zrobi embedding pytania
    n_results=2                 # zwróć 2 najbliższe chunki
)
knowledge = "\n".join(results['documents'][0])
Pułapka, którą warto znać: query zawsze zwróci najbliższe N — nawet jeśli najbliższy dokument jest kompletnie nie na temat. Bez sprawdzenia odległości bot wstrzyknie do promptu śmieci. Rozwiązanie: próg odległości („jeśli najbliższy jest dalej niż X, powiedz że nie wiem"). Opisane w Ulepszeniach — to jedna z najważniejszych poprawek dla graczy.

8 Chunking — dlaczego tniemy tekst

Nie wrzucamy do bazy całych długich stron, tylko kawałki (chunki) po ~150–200 słów, z lekkim nakładem (overlap). Powody:

  • Trafność: krótki chunk = jeden konkretny temat = czystszy wektor. Cała strona miesza tematy.
  • Limit kontekstu: do promptu wkładamy tylko 2–3 chunki, nie całą wiki — model ma ograniczone okno.
  • Overlap: nakładające się słowa na granicy chunków chronią przed przecięciem zdania w połowie myśli.
def chunk_text(text, max_words=200, overlap=30):
    words = text.split()
    chunks, i = [], 0
    while i < len(words):
        chunks.append(" ".join(words[i:i + max_words]))
        i += max_words - overlap        # cofnij się o 30 słów = overlap
    return chunks

Strategie wyszukiwania

  • Czysto wektorowe (obecne): tylko podobieństwo znaczeniowe. Słabe przy dokładnych nazwach/kodach (np. ingot-tinbronze).
  • Hybrydowe (vector + BM25): łączy znaczenie ze zwykłym wyszukiwaniem słów kluczowych. Najlepsze dla recept z konkretnymi nazwami.
  • Reranking (cross-encoder): pobierz 20 kandydatów, potem dokładny model przesortuje top-3. Duży skok trafności.
  • MMR (Maximal Marginal Relevance): dba o różnorodność wyników, by nie dostać 3× tego samego.
