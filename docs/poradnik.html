Ingest danych Vintage Story do ChromaDB

Jak wzbogacić lokalnego AI asystenta o wiedzę z plików gry

Vintage Story — RAG — ChromaDB — Ollama

0 Kontekst projektu

Projekt vs-ai-watchdog to bot działający na serwerze Vintage Story, który nasłuchuje czatu graczy i odpowiada za pomocą lokalnego modelu LLM (Ollama, model gemma3:27b). Żeby odpowiedzi były trafne, bot korzysta z techniki RAG (Retrieval-Augmented Generation) — przed odpowiedzią przeszukuje lokalną bazę wektorową ChromaDB i podaje AI najbardziej pasujące fragmenty wiedzy.

Problem: baza zawierała tylko kilka stron wiki (Casting, Alloying, Bronze, Crucible). Rozwiązanie: zaindeksować bezpośrednio pliki JSON z instalacji gry, które zawierają pełne dane o przedmiotach, blokach i recepturach.

Gracz pisze na czacie
→
watchdog3.py przechwytuje log
→
ChromaDB — szukaj podobnych chunków
→
Ollama (gemma3:27b) generuje odpowiedź
→
RCON wysyła odpowiedź do gry

1 Gdzie są pliki gry

Serwer VS działa w kontenerze Docker o nazwie vs-ai-server (obraz devidian/vintagestory:latest). Pliki gry są dostępne wewnątrz kontenera pod ścieżką /game/assets/survival/.

Pliki można odczytać bez uruchamiania kontenera interaktywnie:

# Wylistowanie plików JSON w katalogu
docker exec vs-ai-server find /game/assets/survival/recipes/alloy -name "*.json"

# Odczyt konkretnego pliku
docker exec vs-ai-server cat /game/assets/survival/recipes/alloy/tinbronze.json

2 Problem: niestandardowy format JSON

Pliki VS nie są poprawnym JSON — używają składni JSON5, czyli m.in. niekwotowane klucze i przecinki na końcu tablic. Standardowy json.loads() w Pythonie rzuca wyjątek. 

// Przykład: tinbronze.json — klucze bez cudzysłowów, przecinek na końcu tablicy
{
    ingredients: [
        { type: "item", code: "ingot-tin", minratio: 0.08, maxratio: 0.12 },
        { type: "item", code: "ingot-copper", minratio: 0.88, maxratio: 0.92 },
    ],
    output: {
        type: "item",
        code: "ingot-tinbronze"
    }
}

Rozwiązanie: biblioteka pyjson5, którą instalujemy w wirtualnym środowisku:

source venv/bin/activate
pip install pyjson5
import pyjson5

def parse_vs_json(raw: str) -> dict | list | None:
    try:
        return pyjson5.loads(raw)
    except Exception:
        return None

3 Filtrowanie danych wizualnych

JSONy VS zawierają ogromną ilość danych renderowania (kształty 3D, transformacje, tekstury, animacje), które są bezużyteczne dla AI i marnują miejsce w bazie. Filtrujemy je, usuwając konkretne klucze ze słownika przed konwersją na tekst. 

VISUAL_KEYS = {
    "shape", "textures", "sounds",
    "groundStorageTransformByType", "fpHandTransform",
    "tpHandTransform", "toolrackTransformByType",
    "guiTransform", "selectionBoxes", "collisionBoxes",
    # ... i kilkanaście innych
}

def strip_visual(obj):
    if isinstance(obj, dict):
        return {k: strip_visual(v) for k, v in obj.items()
                if k not in VISUAL_KEYS}
    if isinstance(obj, list):
        return [strip_visual(i) for i in obj]
    return obj

4 Konwersja JSON na tekst (konwertery)

ChromaDB przechowuje tekst, nie JSON. Dla każdego typu pliku napisany jest oddzielny konwerter, który wyciąga gameplay-owe pola i formatuje je jako czytelne zdania.

Receptura stopu (alloy)

# Wejście (JSON):
# ingredients: [{code: "ingot-tin", minratio: 0.08, maxratio: 0.12}, ...]

# Wyjście (tekst):
Alloy recipe: tinbronze
Ingredients: ingot-tin 8-12%, ingot-copper 88-92%
Output: ingot-tinbronze

Receptura gridowa (crafting)

# Wyjście (tekst):
Grid recipe: anchor
Pattern: HRR,CXR,_FR
Ingredients: H=hammer-* (qty=1), C=chisel-* (qty=1), F=firewood (qty=2), ...
Output: anchor-stone x1

Przedmiot (item)

# Wyjście (tekst):
Item: axe
Tool type: axe
Variants — metal: copper, tinbronze, bismuthbronze, blackbronze, iron, steel
Durability: 800
Mining speed: wood=6, plant=6, soil=1
Dlaczego tekst, a nie JSON?
Model embeddingowy (nomic-embed-text) jest trenowany na naturalnym języku. Tekst opisowy daje lepsze wektory semantyczne niż surowy JSON z nawiasami klamrowymi.

5 Chunking i zapis do ChromaDB

Każdy wygenerowany tekst dzielimy na fragmenty (chunki) o maksimum 200 słów z 30-słowowym nakładem, żeby kontekst nie był ucięty w środku zdania. Następnie zapisujemy do istniejącej kolekcji vintage_story_wiki metodą upsert (zamiast add) — dzięki temu można bezpiecznie uruchomić skrypt ponownie bez duplikatów. 

# ID chunka jest deterministyczny — oparty na nazwie pliku i numerze wpisu
chunk_id = f"{asset_type}_{filename}_{idx}_c{c_idx}"

# Metadane pozwalają filtrować źródło w przyszłości
metadata = {
    "source": "game_asset/recipe_alloy",
    "file": "tinbronze.json",
    "type": "recipe_alloy"
}

# Zapis partiami po 50 (upsert = dodaj lub zaktualizuj)
collection.upsert(documents=chunks, ids=ids, metadatas=metadatas)

7 Rozszerzanie o mody

Mody VS trzymają swoje assety w tej samej strukturze katalogów co vanilla, zazwyczaj wewnątrz pliku .zip w folderze Mods/. Można je wypakować i wskazać ścieżkę w konfiguracji skryptu.

W pliku ingest_game_assets.py wystarczy dodać wpisy do listy ASSET_DIRS:

ASSET_DIRS = [
    # ... oryginalne wpisy vanilla ...

    # Mod: przykładowa ścieżka po wypakowaniu
    ("/game/Mods/mymod/assets/mymod/itemtypes", "item"),
    ("/game/Mods/mymod/assets/mymod/recipes/grid", "recipe_grid"),
]
Uwaga: Po dodaniu moda uruchom skrypt ponownie. Dzięki upsert istniejące chunki zostaną zaktualizowane, a nowe dodane — bez czyszczenia całej bazy.
