Part 01 · The whole system

Architecture

How the game, the bot, the knowledge base and the language model talk to each other — and the short loop the whole bot boils down to.

1 The whole system

The system is made of four parts that talk to each other: the game (Vintage Story in Docker), the bridge to the game (logs + RCON), the brain (a language model) and the memory (the ChromaDB vector database). The diagram shows how information flows when a player asks a question.

The bot is the conductor: it knows nothing and generates nothing itself — it connects the knowledge base to the language model.

2 Two phases: ingest and runtime

This is the key distinction. The project does two quite different things at two different times:

Phase A · once in a while

Ingest (building the knowledge)

You run it by hand when you want to feed the bot. It reads the game files and the wiki, turns them into vectors and stores them in ChromaDB. After that the database is ready until you want to add or refresh knowledge (a game update, a new mod).

Phase B · always running

Runtime (serving players)

The bot runs non-stop as a systemd service, follows the chat and answers as it goes. It uses the database built in phase A. That is bot/watchdog.py.

An analogy: phase A is studying for an exam (writing up notes). Phase B is the exam itself (answering questions with the notes at hand). RAG is an “open-book exam” — the model does not have to remember everything, it looks things up when it needs to.

4 The simplified skeleton (mental model)

watchdog.py can look intimidating (threads, regexes, cooldowns). Strip away everything around the core and a very simple loop remains. This is the whole framework in 12 lines of pseudocode: 

for line in server_logs():               # 1. follow the chat live
    player, question = parse_chat(line)
    if not question: continue

    knowledge = kb.search(question, n=5)   # 2. RAG: find matching chunks

    prompt = f"""You are a Vintage Story assistant.
    Knowledge: {knowledge}
    The player asks: {question}"""       # 3. build the prompt

    answer = llm.generate(prompt)          # 4. ask the model
    rcon.send(answer)                      # 5. post it to chat

Everything else in the real file is support around these 5 steps:

  • A thread pool — questions and event reactions run in worker threads, so the log loop never waits for the LLM.
  • A relevance threshold — chunks that are too far from the question are dropped, and the model is told to say it does not know.
  • Conversation memory — the player's last 3 question/answer pairs, for context.
  • A toxicity filter and cooldowns — no spam, no reacting to abuse.
  • Parsing [CMD: ...] — the model may ask to run time or weather.
  • Reconnecting — if the container restarts, the log stream ends; the bot reconnects after 5 seconds.
Takeaway: if you ever get lost in the code, come back to these 5 steps. Every function in watchdog.py handles exactly one of them, or one of the support pieces above. The reusable parts (config, embeddings, knowledge base, RCON) already live in the shared vsai/ package.

5 Alternative architectures

The project is “RAG glued together by hand”. That is great for learning, but there are other routes:

ApproachWhat it meansWhen it is worth it
Current: a hand-written script You write the loop and call Chroma, Ollama and Gemini over HTTP yourself Learning, full control, few dependencies you are here
A RAG framework
(LangChain / LlamaIndex)		 Ready-made building blocks: loaders, splitters, retrievers, chains When you want to add features quickly (reranking, citations) without writing them from scratch
An agent with tools The model decides when to search the knowledge base and when to run a command (function calling) When you want more autonomous behaviour and more commands
Fine-tuning instead of RAG Bake the knowledge into the model's weights by training (tried here, now in archive/train/) Fine for style and tone. Poor for facts — knowledge goes stale and the model makes things up. combine with RAG
A server mod instead of a bot All logic in C# inside the game, no external process When you want integration from the inside (e.g. an /ai command instead of a chat prefix)
Recommendation: keep the hand-written script (you understand every line), but borrow ideas from the frameworks where they pay off. The relevance threshold is already in; hybrid search and reranking are the next biggest gains — see RAG and the Roadmap.
