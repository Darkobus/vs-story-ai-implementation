1 Ollama — lokalny silnik LLM

Ollama to program, który uruchamia modele językowe na Twoim sprzęcie i udostępnia je przez proste API HTTP. Żadnej chmury, żadnych opłat za tokeny, pełna prywatność. Bot rozmawia z Ollamą zwykłymi zapytaniami HTTP: 

POST http://192.168.0.24:11434/api/generate     # generowanie odpowiedzi
POST http://192.168.0.24:11434/api/embeddings   # zamiana tekstu na wektor
Koszt lokalności: jakość i szybkość zależą od Twojego GPU/CPU. Duży model (gemma3:27b) daje lepsze odpowiedzi, ale wymaga sporo VRAM i jest wolniejszy. To główny kompromis projektu.

2 Dwa modele do dwóch różnych zadań

Łatwo je pomylić, ale robią coś zupełnie innego:

ModelZadanieWejście → wyjście
nomic-embed-text Embedding (rozumienie podobieństwa) tekst → wektor 768 liczb
gemma3:27b / własny Generowanie (pisanie odpowiedzi) prompt → tekst odpowiedzi

Embedding jest „cichym pracownikiem" RAG-u (używany w ingeście i przy każdym pytaniu), a model generujący to „głos" bota. W kodzie: 

MAIN_MODEL      = "vs-god"          # model generujący (po fine-tuningu); fallback: gemma3:27b
TRANSLATE_MODEL = "gemma3:27b"      # do tłumaczenia PL→EN
EMBED_MODEL     = "nomic-embed-text" # do embeddingów
Nazwa vs-god pochodzi od przestarzałej persony „Boga". W Asystencie proponujemy zmianę nazwy i tonu na vs-asystent.

3 Anatomia promptu

Model dostaje jeden sklejony tekst, w którym są wszystkie potrzebne informacje. To tu „dzieje się" RAG — znaleziona wiedza jest doklejana do instrukcji. Struktura:

Cztery warstwy promptu sklejone w jeden string i wysłane do modelu.
system_context = (
    "Jesteś asystentem w grze Vintage Story. "     # ① rola + zasady
    "Odpowiadaj po polsku, zwięźle, max 4 zdania. "
    f"Wiedza z Wiki: {knowledge} "                  # ② RAG
    f"Kontekst rozmowy: {history}"                  # ③ pamięć
)
full_prompt = f"{system_context}\nGracz {player}: {prompt}\nOdpowiedź:"  # ④ pytanie

4 Temperatura — pewność vs kreatywność

temperature steruje „losowością" modelu. Niska = przewidywalne, trzymające się faktów; wysoka = kreatywne, ale częściej zmyśla. Projekt dobiera ją do zadania:

ZadanieTemperaturaDlaczego
Odpowiedzi na pytania (RAG)0.1Chcemy faktów, nie fantazji — trzymaj się wiedzy z bazy
Tłumaczenie PL→EN0.1Tłumaczenie ma być wierne, nie twórcze
Klimatyczne reakcje na zdarzenia0.7Tu chcemy różnorodności, żeby się nie powtarzać
Dla asystenta-od-faktów niska temperatura to sojusznik. Jeśli kiedyś bot zacznie zmyślać receptury — najpierw sprawdź, czy RAG zwrócił sensowną wiedzę, a potem czy temperatura nie jest za wysoka.

5 Krok tłumaczenia PL→EN (i jak go usunąć)

Baza wiedzy jest po angielsku (pliki gry, wiki), a gracze piszą po polsku. Embedding polskiego pytania słabo pasowałby do angielskich chunków. Obecne rozwiązanie: najpierw przetłumacz pytanie na angielski, dopiero potem szukaj. 

def translate_query_for_rag(prompt):
    # wyślij do modelu: "Translate this game question to English: ..."
    return ollama_generate(TRANSLATE_MODEL, prompt, temperature=0.1)
Ten krok jest kruchy i kosztowny:
  • Dokłada całe dodatkowe wywołanie dużego LLM przed każdym pytaniem → wolniej.
  • Jak się zepsuje/przekręci słowo (np. „brąz" → „brown" zamiast „bronze") → RAG szuka nie tego.
  • To kolejny punkt awarii w łańcuchu.
Lepsze rozwiązanie (mocno polecane): użyj wielojęzycznego modelu embeddingowego (np. bge-m3). Taki model rozumie polski i angielski w tej samej przestrzeni wektorowej — polskie pytanie trafi obok angielskiego chunku bez tłumaczenia. Cały krok translate_query_for_rag znika, a bot przyspiesza i przestaje się gubić na słowach. Szczegóły w Ulepszeniach.

6 Fine-tuning: własny model

W katalogu train/ jest pełen potok robienia własnego modelu dotrenowanego na stylu bota. Idea: wziąć gotowy model bazowy (Qwen2.5-7B) i „doszlifować" go przykładami, jak ma odpowiadać.

generate_data.py
tworzy przykłady Q&A
→
finetune.py
trening LoRA (QLoRA 4-bit)
→
eksport do
GGUF
→
Modelfile
ollama create
  • generate_data.py — generuje pary pytanie/odpowiedź z bazy (model-nauczyciel gemma3:27b) plus ręczne przykłady stylu i komend.
  • finetune.py — LoRA/QLoRA: zamiast trenować cały model (miliardy wag), uczy tylko małe „nakładki". Mieści się w 16 GB VRAM.
  • Modelfile — przepis dla Ollamy: bierze plik GGUF, ustawia temperaturę i prompt systemowy, tworzy model vs-god.
# LoRA = trenujemy tylko cienkie "adaptery", nie cały model
LORA_R = 32          # "grubość" adaptera — większa = lepsza jakość, więcej VRAM
load_in_4bit = True   # kwantyzacja 4-bit (Q) w QLoRA — oszczędza pamięć
Po co fine-tuning, skoro jest RAG? Fine-tuning uczy stylu i formatu (zwięzłość, ton, użycie [CMD:]), a nie faktów. To dwie różne dźwignie — patrz tabela niżej.

7 RAG vs fine-tuning — kiedy co

RAGFine-tuning
UczyFaktów (wiedza)Stylu, tonu, formatu
AktualizacjaŁatwa — zmień wpis w bazieTrudna — trzeba trenować od nowa
HalucynacjeOgranicza (podaje źródła)Nie pomaga, czasem pogarsza
KosztNiski (tylko baza)Wysoki (GPU, czas, dane)
Najlepsze do„Jaka jest receptura X?"„Mów krótko, po polsku, w tym stylu"
Złota zasada: fakty przez RAG, styl przez fine-tuning. Najlepszy efekt daje połączenie obu — ale fine-tuning jest opcjonalny. Sam RAG + dobry prompt systemowy (patrz Asystent) wystarcza, by bot był użyteczny.
