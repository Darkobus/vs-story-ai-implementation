1 Two models for two jobs

They are easy to mix up, but they do completely different things:

ModelJobInput → outputRuns on
bge-m3 Embedding (measuring similarity) text → vector of 1024 numbers Ollama on the game server (CPU is fine)
gemini-2.5-flash / gemma3:12b Generation (writing the answer) prompt → answer text Gemini API, or Ollama on the PC

The embedding model is the quiet worker behind RAG (used by ingest and for every question); the generation model is the bot's voice. Keeping embeddings on the server means retrieval works even when the PC is off.

The knowledge base can only be searched with the model that built it. The collection records it (embed_model), and the bot refuses a mismatch — change OLLAMA_EMBED_MODEL only together with a rebuild.

2 Generation: Gemini or Ollama

generate_text() picks the backend from the environment. With GEMINI_API_KEY set, answers come from Gemini 2.5 Flash; without it, from gemma3:12b in Ollama on the PC (OLLAMA_PC_HOST). 

def generate_text(prompt, temperature=0.1, timeout=90, model=None):
    if not USE_GEMINI:
        return _ollama_generate(prompt, temperature, timeout)
    try:
        return _gemini_generate(prompt, temperature, timeout, model or GEMINI_MODEL)
    except Exception:
        if not OLLAMA_FALLBACK:       # OLLAMA_FALLBACK=1 → try Ollama when Gemini fails
            raise
        return _ollama_generate(prompt, temperature, timeout)
  • Gemini — fast and good at Polish; thinking is turned off (thinkingBudget: 0) and output is capped at 400 tokens to keep answers quick and cheap. The API key goes in the x-goog-api-key header, so it never shows up in a URL or a log.
  • Ollama — free and private, but the quality and speed depend on the GPU. gemma3:12b (~8 GB) fits in 16 GB of VRAM; gemma3:27b does not, spills to the CPU and times out.
  • The fallback is off by default: with the PC switched off, every failed Gemini call would also wait for an Ollama timeout.
Gemini answers that come back blocked or empty (safety filter, token limit) raise a clear error with the reason, instead of failing with a KeyError deep in the response.

3 Anatomy of the prompt

The model receives one string with everything it needs. This is where RAG actually happens — the retrieved knowledge is pasted next to the instructions. The prompt is written in English; one of the rules tells the model to reply in Polish.

Four layers glued into one string and sent to the model.
system_context = (
    "You are a helpful assistant on a Vintage Story game server. Rules: "   # ① role + rules
    "1. Always reply in Polish, naturally and in a friendly way. "
    "2. Give the concrete answer first, concisely, at most 4 sentences. "
    "3. Base your answer PRIMARILY on the 'Wiki knowledge' below ... "
    "4. Vintage Story is NOT Minecraft ... "
    "5. If the knowledge below does not contain the answer, say plainly ... "
    ...
    f"Wiki knowledge: {knowledge or NO_KNOWLEDGE} "                   # ② RAG
    f"Conversation context: {history}"                                  # ③ memory
)
full_prompt = f"{system_context}\nPlayer {player}: {prompt}\nAnswer:"   # ④ question

The full rule list and the reasoning behind it are on the Persona page.

4 Temperature — precision vs creativity

temperature controls how random the model is. Low = predictable and close to the facts; high = creative, but more likely to make things up. The bot picks it per task:

TaskTemperatureWhy
Answering questions (RAG)0.1Facts, not fantasy — stick to the knowledge base
Gameplay tips (autonomous loop)0.1They go through the same ask_ai() path, grounded in the knowledge base
Reactions to events0.7Variety, so greetings and storm warnings do not repeat word for word
For a fact assistant, low temperature is your friend. If the bot ever starts inventing recipes, first check what RAG returned (the distances in the log), then whether the temperature is too high.

5 The PL→EN translation step (and why it is gone)

The knowledge base is in English (game files, wiki); players write in Polish. With the old English-only embedding model (nomic-embed-text), a Polish question landed far from the English chunks, so every question was first translated to English by an LLM, and only then searched.

That step was fragile and slow:
  • A whole extra LLM call before every question.
  • A mistranslated word (“brąz” → “brown” instead of “bronze”) sent RAG looking for the wrong thing.
  • One more point of failure in the chain.
Now: the embedding model is multilingual (bge-m3). It maps Polish and English into the same vector space, so a Polish question lands next to the matching English chunk without translation. The step is off by default; RAG_TRANSLATE=1 turns it back on if a comparison is ever needed.

6 Fine-tuning (archived)

The project once trained its own model: a base model (Qwen2.5-7B) fine-tuned on question/answer examples, exported to GGUF and loaded into Ollama as vs-god. The code is kept in archive/train/ for reference, but it is no longer used or maintained.

  • LoRA/QLoRA trains only small “adapters” instead of all the model's weights, so it fits in 16 GB of VRAM.
  • Why it was retired: it taught the old “god” persona, it depended on the old knowledge base and embedding model, and a good prompt over RAG gave better, more up-to-date answers with none of the training cost. See archive/README.md.

7 RAG vs fine-tuning — when to use which

RAGFine-tuning
TeachesFacts (knowledge)Style, tone, format
UpdatingEasy — re-ingestHard — retrain
HallucinationsReduces them (answers from sources)Does not help, sometimes worse
CostLow (just the database)High (GPU, time, data)
Best for“What is the recipe for X?”“Answer briefly, in this style”
Rule of thumb: facts through RAG, style through fine-tuning — and with a capable model, style through the prompt is usually enough. That is where this project ended up.
