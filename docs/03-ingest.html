Ingest danych do bazy

1 Po co to robimy

Bot jest mądry tylko na tyle, na ile mądra jest jego baza. Ingest to proces napełniania bazy wektorowej wiedzą o grze: recepturami, przedmiotami, blokami, stronami wiki. Bez tego kroku query() nie ma czego zwracać.

Ingest uruchamiasz ręcznie i rzadko — np. po aktualizacji gry albo dodaniu moda. W codziennej pracy bota ten kod w ogóle się nie wykonuje.

2 Dwa źródła wiedzy

ingest/game_assets.py

Pliki gry (JSON)

Czyta definicje z wnętrza kontenera Dockera (przez docker exec): receptury stopów, craftingu, kucia, gotowania, beczek + przedmioty i bloki. To „twarde dane" gameplay'owe — dokładne proporcje, dropy, trwałość.

ingest/wiki.py

Strony wiki (tekst)

Czyta pliki tekstowe wiki, czyści składnię MediaWiki (linki [[...]], szablony {{...}}, pogrubienia). To „wiedza opisowa": mechaniki, poradniki, lore.

Oba wrzucają dane do tej samej kolekcji vintage_story_wiki, więc bot przeszukuje je razem.

4 Pułapka: niestandardowy JSON5

Pliki Vintage Story nie są poprawnym JSON — używają składni JSON5: klucze bez cudzysłowów i przecinki na końcu list. Zwykłe json.loads() rzuca błędem. Dlatego projekt używa biblioteki pyjson5: 

import pyjson5

def parse_vs_json(raw: str):
    try:
        return pyjson5.loads(raw)   # radzi sobie z JSON5
    except Exception:
        return None             # uszkodzony plik → pomiń

Czyszczenie danych wizualnych

Definicje przedmiotów zawierają mnóstwo danych renderowania (kształty 3D, tekstury, animacje, transformacje), które są bezużyteczne dla AI i tylko zaśmiecają wektory. Usuwamy je po kluczach przed konwersją: 

VISUAL_KEYS = {"shape", "textures", "sounds", "guiTransform",
               "collisionBoxes", "selectionBoxes", ...}  # ~40 kluczy

def strip_visual(obj):
    if isinstance(obj, dict):
        return {k: strip_visual(v) for k, v in obj.items()
                if k not in VISUAL_KEYS}
    if isinstance(obj, list):
        return [strip_visual(i) for i in obj]
    return obj

5 Dlaczego zamieniamy JSON na zdania

Model embeddingowy był trenowany na naturalnym języku, nie na nawiasach klamrowych. Opisowy tekst "Alloy recipe: tinbronze, Ingredients: ingot-tin 8-12%..." daje znacznie lepszy wektor semantyczny niż surowy JSON. Dlatego dla każdego typu pliku jest osobny konwerter:

KonwerterTyp plikuCo wyciąga
convert_alloyreceptury stopówskładniki + proporcje %, wynik
convert_gridcraftingwzór gridowy, składniki, ilość wyniku
convert_smithingkucieskładnik, dozwolone metale, wynik
convert_cookinggotowanieskładniki, ilości, co powstaje
convert_itemprzedmiotytyp narzędzia, trwałość, warianty, obrażenia, odżywianie
convert_blockblokimateriał, twardość, dropy, zachowania
Zasada uniwersalna RAG: jakość bazy = jakość tekstu, który do niej wkładasz. „Garbage in, garbage out". Dobre, opisowe chunki to 80% sukcesu RAG-u — ważniejsze niż wybór bazy czy modelu.

6 Upsert vs add — bez duplikatów

game_assets.py używa upsert (dodaj lub zaktualizuj), a nie add. Dzięki deterministycznym ID możesz uruchomić ingest ponownie bez tworzenia duplikatów: 

chunk_id = f"{asset_type}_{filename}_{idx}_c{c_idx}"   # zawsze takie samo dla tego samego wpisu

collection.upsert(
    documents=chunks,
    ids=ids,           # jeśli ID istnieje → nadpisz, jeśli nie → dodaj
    metadatas=metas    # {"source":..., "file":..., "type":...}
)
Uwaga na wiki.py: on używa add (nie upsert) — ponowne uruchomienie na tych samych plikach doda duplikaty. Drobny kandydat na ujednolicenie (patrz Ulepszenia).

Metadane — po co

Każdy chunk dostaje metadane (source, file, type). Dziś nie są mocno używane, ale pozwalają w przyszłości filtrować („szukaj tylko w recepturach") i cytować źródło w odpowiedzi („wg wiki: Smithing").
