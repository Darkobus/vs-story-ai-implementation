Part 03 · Building the knowledge

Loading data into the knowledge base

How raw game files and wiki pages become searchable knowledge in ChromaDB. This is “phase A” from the architecture — run when you want to feed the bot.

1 Why we do this

The bot is only as smart as its database. Ingest is the process of filling the vector database with game knowledge: recipes, items, blocks and wiki pages. Without it, query() has nothing to return.

You run ingest by hand and rarely — after a game update, for example. While the bot is running, this code is not used at all.

2 Two sources of knowledge

ingest/game_assets.py

Game files (JSON)

Reads the definitions either from inside the game's Docker container (docker exec … tar) or from a local copy of the assets (--assets-dir). Alloy, crafting, smithing, cooking and barrel recipes, plus items and blocks. This is the hard gameplay data — exact ratios, drops, durability.

ingest/wiki.py

Wiki pages (text)

Downloads pages from the official wiki through the MediaWiki API — a curated list by default, or the whole wiki with --all (--en keeps English pages only). Cleans the markup. This is the descriptive knowledge: mechanics, guides, lore.

Both write to the same collection, vintage_story_kb, so the bot searches them together.

Where the game files live

In the vs-ai-server container the assets are under /game/assets/survival/ (approximate vanilla file counts):

For example, one alloy recipe file goes through the whole pipeline and ends up in the database as a readable sentence:

# input — tinbronze.json (raw game file, JSON5 syntax)
{ ingredients: [
    { code: "ingot-tin",    minratio: 0.08, maxratio: 0.12 },
    { code: "ingot-copper", minratio: 0.88, maxratio: 0.92 },
  ], output: { code: "ingot-tinbronze" } }

# output — the text stored in the database
Alloy recipe: tinbronze
Ingredients: ingot-tin 8-12%, ingot-copper 88-92%
Output: ingot-tinbronze

4 A trap: non-standard JSON5

Vintage Story files are not valid JSON — they use JSON5 syntax: unquoted keys and trailing commas. Plain json.loads() fails on them. That is why the project uses pyjson5: 

import pyjson5

def parse_vs_json(raw: str):
    try:
        return pyjson5.loads(raw)   # handles JSON5
    except Exception:
        return None             # broken file → skip it and count an error

Stripping visual data

Item and block definitions are full of rendering data (3D shapes, textures, animations, transforms) that means nothing to the AI and only pollutes the vectors. It is removed by key before conversion: 

VISUAL_KEYS = {"shape", "textures", "sounds", "guiTransform",
               "collisionBoxes", "selectionBoxes", ...}  # ~45 keys

def strip_visual(obj):
    if isinstance(obj, dict):
        return {k: strip_visual(v) for k, v in obj.items()
                if k not in VISUAL_KEYS}
    if isinstance(obj, list):
        return [strip_visual(i) for i in obj]
    return obj

5 Why we turn JSON into sentences

The embedding model was trained on natural language, not curly braces. Descriptive text like "Alloy recipe: tinbronze, Ingredients: ingot-tin 8-12%..." gives a much better semantic vector than raw JSON. So each file type has its own converter:

ConverterFile typeWhat it extracts
convert_alloyalloy recipesingredients + ratio ranges (rounded %), output
convert_gridcraftinggrid pattern, ingredients, output quantity
convert_smithingsmithingingredient, allowed metals, output
convert_cookingcookingingredients, quantities, result
convert_barrelbarrel recipesingredients, output, duration
convert_itemitemstool type, durability (per variant), variants, damage, nutrition
convert_blockblocksmaterial, resistance (per variant), drops, behaviours
The universal rule of RAG: the quality of the database is the quality of the text you put in. Garbage in, garbage out. Good, descriptive chunks matter more than the choice of database or model.

6 Cleaning wiki pages

Raw wikitext is mostly markup. clean_mediawiki_text() keeps the prose and the facts:

  • Infoboxes ({{Item|durability=…}}) become key: value lines, minus image/icon/link fields.
  • Link-style templates keep their display text ({{ll|Casting|smelted}} → smelted); templates without parameters ({{PT}}) are dropped; wiki links [[Target|label]] keep only the label; table cells keep their contents.
  • Comments, <translate>/<languages> tags, galleries, references, and File/Image/Category links are removed.
  • Redirect pages are skipped.
  • Each chunk starts with Wiki page: <title>, so even a chunk from the middle of a page says what it is about.

7 Re-ingesting without duplicates

Both scripts can be run again safely. Chunk IDs are deterministic and include the file's path relative to the asset folder — file names alone are not unique (several folders contain a generic.json): 

chunk_id = f"{asset_type}:{rel_path}:{idx}:{c_idx}"   # game assets
chunk_id = f"wiki:{title}:{n}"                       # wiki pages

And before writing, the old chunks of the same source are deleted, so a file that was removed or a page that got shorter leaves nothing stale behind:

collection.delete(where={"type": asset_type})                # game assets: one asset type at a time
collection.delete(where={"source": {"$in": sources}})        # wiki: the pages in this batch
kb.add_documents(collection, ids, texts, metadatas)          # embed in batches + upsert
Embedding failures are not hidden. If Ollama fails on a batch, that batch is skipped and counted — it is never stored with zero vectors, which would match random questions later.

Metadata

Each chunk carries source (e.g. game_asset/recipe_alloy/tinbronze.json or wiki/Bronze) and type; wiki chunks also get a url. The bot logs sources next to distances, and cites them to players at the end of an answer.

8 Running it

# from the repo root, with the venv active
python -m ingest.game_assets --dry-run            # parse only, print samples, write nothing
python -m ingest.game_assets --reset              # fresh collection + all game assets (from the container)
python -m ingest.game_assets --assets-dir PATH    # from a local assets folder instead
python -m ingest.wiki --all --en                  # the whole English wiki

python -m tools.dbcheck "jak zrobić brąz"          # check what comes back, and at what distance
--reset drops the whole collection, wiki included. Run it with the game-assets script first, then the wiki. Embedding needs ollama pull bge-m3 on the machine in OLLAMA_EMBED_HOST.
